# resilient-api-client

Клієнт зовнішнього API для нічної синхронізації: таймаут на кожну спробу, повтори з наростаючою паузою,
повага до `Retry-After`, зрозумілі помилки. TypeScript (strict), Node.js ≥ 20, без залежностей (вбудований `fetch`).

```ts
import { ApiError, requestJson } from "./src/client.js";

try {
  const stats = await requestJson<Stats>("https://api.example.com/stats?day=2026-11-24", {
    init: { headers: { authorization: `Bearer ${token}` } },
    timeoutMs: 10_000, // на кожну спробу
    maxAttempts: 5,    // разом з першою
    deadlineMs: 120_000, // на все разом: спроби і паузи
  });
} catch (e) {
  if (e instanceof ApiError) console.error(e.kind, e.status, e.message);
  throw e;
}
```

Повний приклад нічної задачі, яка розрізняє «API лежить» і «токен протух»: [`examples/nightly-sync.ts`](examples/nightly-sync.ts).

```
npm install
npm test           # без зовнішньої мережі
npm run typecheck  # tsc, strict
npm run lint       # eslint + typescript-eslint
npm run build
```

## Поведінка

| Ситуація | Що робимо |
|---|---|
| 2xx | Розбираємо JSON і повертаємо |
| 5xx, 408, мережева помилка, таймаут | Повтор, пауза `base·2^(n-1)` (з обмеженням `maxDelayMs`) та jitter |
| 429 (і 503) з `Retry-After` | Чекаємо стільки, скільки просить сервер (секунди або HTTP-дата) |
| 429 без/з некоректним `Retry-After` | Звичайний backoff |
| 401 / 403 | **Без повторів**, `ApiError{kind:"auth_error"}`: токен протух або без прав, це має побачити людина |
| Інші 4xx | **Без повторів**, `ApiError{kind:"client_error"}` з кодом, URL і початком тіла відповіді |
| Спроби вичерпано | `retries_exhausted`: кількість спроб, останній статус, початок тіла відповіді, `cause` |
| Наступна пауза не вміщається в `deadlineMs` | `deadline_exceeded` (наприклад, `Retry-After: 86400`), без сну |
| POST/PATCH: 5xx або таймаут | `unsafe_to_retry`: запит міг уже виконатися, повторювати не можна. Після 429 повторюємо |
| 2xx, але тіло не JSON | `invalid_response`, без повторів |

## Рішення і чому

- **Ліміт спроб і загальний дедлайн.** `maxAttempts` (за замовчуванням 5) рахує всі спроби, зокрема 429.
  `deadlineMs` (2 хв) обмежує загальний час: таймаут спроби не перевищує залишку, а пауза, що не вміщається, не
  виконується. Нескінченний цикл неможливий, навіть якщо сервер вічно просить «зачекай».
- **Таймаут на спробу покриває і читання тіла.** Свій `AbortController` + `setTimeout`, таймер знімається у `finally`.
  Сервер, що віддав заголовки й завис посеред відповіді, теж дає таймаут (є тест на реальному локальному сервері).
- **Exponential backoff з jitter.** Половина паузи фіксована, половина випадкова: клієнти, що впали одночасно, не б'ють по
  API синхронно, але пауза не стає майже нульовою.
- **`Retry-After` важливіший за backoff**, бо сервер знає краще. Для 503 так само: сервери часто віддають заголовок саме з ним.
- **4xx не повторюємо**: запит однаково буде відхилений. Помилка містить статус, URL і відповідь сервера. 401/403 винесено
  в окремий вид `auth_error`, щоб протухлий токен не губився серед решти помилок.
- **408 повторюється.** Це відхилення від букви завдання («4xx крім 429 не повторювати»): 408 означає таймаут, а
  таймаути за завданням повторюються. Щоб повернути строгу поведінку, достатньо прибрати `status === 408` у `client.ts`.
- **Повтор лише безпечних методів.** GET/HEAD/OPTIONS/PUT/DELETE повторюються; POST/PATCH після таймауту чи 5xx ні, бо
  сервер міг уже обробити запит. Після 429 повторюється будь-який метод: сервер його не виконував.
- **Секрети не потрапляють у логи.** Ключі API часто передають у query-рядку, тому в тексті помилок і в `details.url`
  лишається тільки `origin + path`. Сам запит іде з повним URL.
- **Тестованість.** `fetch`, `sleep`, `random`, `now` підміняються через `deps`, тому тести не чекають реальні секунди
  й детерміновані (наприклад, при `random=0` паузи рівно 250/500/1000 мс). Дати в тестах прибиті.
- **Скільки в API опцій.** Лише те, що потрібне для завдання: таймаут, ліміт спроб, параметри паузи, дедлайн, `init`.

## Тести (`test/`)

- `client.test.ts`: мок `fetch` зі сценарієм відповідей. Успіх, 5xx → успіх, зростання пауз і їхня межа, мережеві помилки,
  408, таймаут із реальним скасуванням запиту, `Retry-After` (секунди/дата/некоректний), вічний 429 і вічний 500
  зупиняються рівно на `maxAttempts`, 4xx і 401/403 без повторів, секрет у URL, загальний дедлайн, ідемпотентні та
  неідемпотентні методи, невалідний JSON, відсутність завислих таймерів.
- `local-server.test.ts`: справжній `fetch` проти локального сервера, який мовчить, зависає посеред тіла, віддає 500 і 429,
  а потім 200; плюс 404 без повторів. Сервер закриває з'єднання після кожної відповіді (`Connection: close`): з keep-alive
  я бачив, що наступний запит зрідка доходив до сервера вже після таймауту. Першопричину в `undici` не з'ясовував,
  для клієнта це якраз той випадок, який повтор і має поглинати.

## Що перевірено

- Локально: `lint`, `typecheck`, тести, `build`; 15 повних запусків поспіль і 12 паралельних без жодного збою.
- Чистий клон репозиторію: `npm ci` і всі перевірки проходять без локальних файлів.
- CI на GitHub Actions ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)): Node 20, 22, 24 на Linux і Node 22 на Windows.
- **Не перевірено:** реальний зовнішній API (у завданні його немає), поведінка під великим навантаженням, macOS.
  Значення за замовчуванням (таймаут 10 с, дедлайн 2 хв, 5 спроб) підібрано на око, їх треба звірити з реальним API.

## Робота з Claude Code

Код, тести й цей README написано разом із Claude Code (ШІ-агент для коду). Як це було:

- Завдання, вимоги й базу знань компанії дав я. Агент написав першу версію клієнта й тестів.
- Потім агент звірив результат з базою знань AlphaDOM. Знайшли й виправили: секрети в URL могли потрапити в лог,
  протухлий токен не відрізнявся від решти 4xx, не було лінтера.
- Тести самі знайшли баг: `Retry-After: -3` читався як дата, і клієнт не чекав зовсім. Нестабільний тест на локальному
  сервері теж знайшли прогонами в циклі, а не з першого разу.
- Після цього прибрали все зайве, чого завдання не вимагає (власний парсер, колбек `onRetry`, зовнішній abort-сигнал,
  окремий ліміт `Retry-After`), і додали загальний дедлайн, повтор лише безпечних методів, CI та приклад.
- Усі перевірки (тести, типи, лінтер, збірка, чистий клон) запускав агент у моєму середовищі; ті самі кроки тепер бігають у CI.
  Відповідаю за код я.
