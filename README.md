# resilient-api-client

Клієнт зовнішнього API для нічної синхронізації: таймаут на кожну спробу, повтори з наростаючою паузою,
повага до `Retry-After`, зрозумілі помилки. TypeScript, Node.js ≥ 20, без залежностей (вбудований `fetch`).

```ts
import { requestJson, ApiError } from "./src/client.js";

try {
  const stats = await requestJson<Stats>("https://api.example.com/stats?day=2026-11-24", {
    init: { headers: { authorization: `Bearer ${token}` } },
    timeoutMs: 10_000,   // на кожну спробу
    maxAttempts: 5,      // разом з першою
    onRetry: ({ attempt, delayMs, reason }) => log.warn(`retry #${attempt} in ${delayMs} ms: ${reason}`),
  });
} catch (e) {
  if (e instanceof ApiError) log.error(e.kind, e.status, e.message);
  throw e;
}
```

npm install
npm test           # 40 тестів, без зовнішньої мережі
npm run typecheck  # tsc, strict
npm run lint       # eslint + typescript-eslint

## Поведінка

| Ситуація | Що робимо |
|---|---|
| 2xx | Розбираємо JSON і повертаємо |
| 5xx, мережева помилка, таймаут | Повтор, пауза `base·2^(n-1)` (з обмеженням `maxDelayMs`) та jitter |
| 429 (і 503) з `Retry-After` | Чекаємо рівно стільки, скільки просить сервер (секунди або HTTP-дата) |
| 429 без/з некоректним `Retry-After` | Звичайний backoff |
| 401 / 403 | **Без повторів**, `ApiError{kind:"auth_error"}`: токен протух або без прав, це має побачити людина, а не нічний цикл |
| Інші 4xx | **Без повторів**, одразу `ApiError{kind:"client_error"}` з кодом, URL і початком тіла відповіді |
| Спроби вичерпано | `ApiError{kind:"retries_exhausted"}` з кількістю спроб, останнім статусом і `cause` |
| `Retry-After` > `maxRetryAfterMs` | `ApiError{kind:"retry_after_too_long"}` — не засинаємо на годину |
| 2xx, але тіло не JSON | `invalid_response`, без повторів |
| `AbortSignal` від викликача | `aborted`, перериває і запит, і паузу |

## Рішення і чому

- **Ліміт спроб — єдиний цикл виходу.** `for` завершується або успіхом, або `throw`; `maxAttempts` (за замовчуванням 5)
  рахує *всі* спроби, зокрема 429. Постійний 429 чи постійний 500 не можуть зациклити нічний job. Валідація:
  `maxAttempts` має бути цілим ≥ 1.
- **Таймаут на спробу, і він покриває читання тіла.** Власний `AbortController` + `setTimeout`, таймер знімається у
  `finally`. Тіло читається всередині спроби: сервер, що віддав заголовки й завис посеред відповіді, теж дає таймаут
  (є тест на реальному локальному сервері).
- **Exponential backoff з jitter.** Половина паузи фіксована, половина випадкова («equal jitter»): клієнти, що впали
  одночасно, не б'ють по API синхронно, але пауза не стає майже нульовою. Є верхня межа `maxDelayMs`.
- **`Retry-After` має пріоритет над backoff**, бо сервер знає краще. Підтримані обидва формати (секунди й дата).
  Для 503 робимо те саме: сервери часто віддають `Retry-After` саме з ним. Є ліміт `maxRetryAfterMs`: якщо API
  просить чекати добу, краще чесно впасти, ніж висіти.
- **4xx крім 429 не повторюємо**: запит однаково буде відхилений (поганий токен, відсутній ресурс). Помилка містить
  статус, URL і відповідь сервера, щоб причину було видно в логах без дебагу. Я навмисно не повторюю й 408, щоб
  дотримуватися вимоги буквально; додати його до повторів — один рядок.
- **Секрети не потрапляють у логи.** Ключі API часто передають у query-рядку, тому в тексті помилок і в `details.url`
  лишається тільки `origin + path`. Сам запит іде з повним URL (є тест на обидва боки).
- **Типізовані помилки.** `ApiError.kind` дає змогу викликачу розрізняти «наш запит кривий» (виправити код/токен) і
  «API лежить» (повторити синхронізацію пізніше) без розбору рядків.
- **Невалідне 2xx не повторюємо**: це баг на боці API, а не збій, який минає. Обірване з'єднання під час читання тіла
  йде як мережева помилка і повторюється.
- **Тестованість.** `fetch`, `sleep`, `random`, `now` можна підмінити, тому тести не чекають реальні секунди й
  детерміновані (наприклад, при `random=0` паузи рівно 250/500/1000 мс).

## Тести (`test/`)

- `client.test.ts`: мок `fetch` зі сценарієм відповідей: успіх, 5xx → успіх, зростання пауз і їхня межа, мережеві помилки,
  таймаут із реальним скасуванням запиту, `Retry-After` (секунди/дата/некоректний/занадто великий), вічний 429 і вічний 500
  зупиняються рівно на `maxAttempts`, 4xx і 401/403 без повторів, невалідний JSON, секрет у URL, скасування під час
  запиту й під час паузи, відсутність завислих таймерів. Дати в тестах прибиті (`now` підміняється), реальні секунди
  не чекаємо (`sleep` підміняється).
- `local-server.test.ts`: справжній `fetch` проти локального сервера, який мовчить, зависає посеред тіла, віддає 500 і 429,
  а потім 200; плюс 404 без повторів.

## Що перевірено і як

- **Зроблено:** клієнт, 40 тестів, типи (strict), лінтер, збірка (`tsc`).
- **Мутаційна перевірка** (прийом з бази знань «тест має падати без виправлення»): по черзі ламав код у 22 місцях
  (4xx повторюється, немає таймауту, ігнорується `Retry-After`, зайва спроба, немає експоненти, немає jitter, `-3` читається
  як дата, секрет у помилці, таймер не знімається, пауза не переривається при abort тощо). **Усі 22 мутації валять тести.**
  Скрипт одноразовий і не входить у репозиторій. Перед цим я підсилив два слабкі тести: abort під час паузи (раніше
  проходив би і з зламаним кодом, бо перевірка стоїть і на вході в цикл) та перевірку, що не лишається таймерів.
- **Лінтер перевірено, що він справді падає** на штучній помилці (щоб не було «гейта, що ніколи не запускався»).
- **Флейк, який я знайшов:** тест на локальному сервері зрідка (~1 запуск з 8) падав: на keep-alive з'єднанні
  наступний запит доходив до сервера вже після нашого таймауту 150 мс. З `Connection: close` на сервері 0 збоїв з 80
  запусків, 12 повних запусків поспіль зелені. Мій `body.cancel()` не винен (перевірив, без нього так само).
  Першопричину в `undici`/Windows до кінця не з'ясовував. Для клієнта це якраз той випадок, який повтор і має
  поглинати, а в тесті з'єднання закриваються, щоб він був детермінованим.
- **Не перевірено:** реальний зовнішній API (у завданні його немає); поведінка під великим навантаженням; Linux/macOS
  (бігав лише на Windows 11, Node 26); `maxRetryAfterMs` за замовчуванням (120 с) підібрано на око.

## Обмеження

- Повтори безпечні для ідемпотентних запитів (GET за статистикою). Для POST без ключа ідемпотентності повтор
  після таймауту може продублювати дію. Потоки в `body` не можна відтворити, тому передавайте рядок/буфер.
- Код більший за «50 рядків» з бази знань: частина обсягу це точки підміни (`fetch`, `sleep`, `random`, `now`), без яких
  тести довелося б робити повільними й недетермінованими. Якщо ментор вважає опції `parse`/`onRetry` зайвими, їх можна прибрати.
- Загальний час у гіршому випадку ≈ `maxAttempts·timeoutMs` + сума пауз; за потреби обмежте його зовнішнім `AbortSignal`.
